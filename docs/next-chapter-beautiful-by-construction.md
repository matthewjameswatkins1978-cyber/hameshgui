# Hamesh: Beautiful and Understandable by Construction
**Research and parked implementation roadmap — 2026-11-24**
**Status: proposed next campaign, NOT an active sprint or permission to start agents.**

## 1. Decision and product definition
Hamesh becomes a native **semantic presentation framework**: meaning in, high-quality visual composition out, actual resolved state and typed capabilities available to humans and agents. AI-first, not AI-dependent. The author specifies meaning, data, relative importance, relationships and capabilities; a deterministic design system owns normal styling and responsive composition. Human users retain control. An expert escape hatch for creative canvases and bespoke controls is legitimate but explicit, testable and not the default authoring path.
Do not optimise for looking like a chat product everywhere. Desktop menus, dense editors, tools and artwork require different presentation recipes. The five visual worlds are a useful asset, not a mandate to polish five themes at once. The goal is multiple coherent looks, not universal rounded cards.
Do not promise automatic beauty, perfect perception or guaranteed model correctness. Guarantee specific constraints, expose violations and test aesthetic outcomes with actual rendered examples. No screenshots required for ordinary discovery, layout inspection, or actions. Selective screenshots/audio are useful for independent fidelity and perceptual questions.

## 2. Research and reuse
No private OpenAI implementation inspected; the user's screenshot is a reference outcome, not a claim about internal implementation. Public sources and transferable techniques:
- [OpenAI UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines), [Apps SDK UI](https://github.com/openai/apps-sdk-ui), [public UI integration guide](https://developers.openai.com/plugins/build/chatgpt-ui): curated components, host-owned theme, restrained hierarchy and selecting the appropriate presentation format. Study the actual library's typography/spacing/component recipes and accessibility tests; do not port React/Tailwind wholesale or copy OpenAI branding.
- [A2UI introduction](https://developers.googleblog.com/en/introducing-a2ui-an-open-project-for-agent-driven-interfaces/), [A2UI 1.0](https://developers.googleblog.com/a2ui-10-build-delightful-fast-reliable-agentic-experiences/), [catalogue](https://a2ui.org/concepts/components/), [data binding](https://a2ui.org/concepts/data-binding/): trusted typed catalogues, allowed placement, stable component IDs, separate data, event roundtrips, incremental changes, renderer-owned display. Study interoperability with 1.0 after internal semantics are proven. A2UI adapter is optional; not the domain core.
- [Adaptive Cards](https://learn.microsoft.com/en-us/adaptive-cards): host-specific presentation of portable structured content, responsive variants. Avoid lowest-common-denominator design.
- [Adobe Spectrum tokens](https://spectrum.adobe.com/page/design-tokens), [GOV.UK type scale](https://design-system.service.gov.uk/styles/type-scale/), [DTCG stable specification](https://www.designtokens.org/TR/2025.10/): semantic/alias tokens, typographic ramps, contextual density and measured responsive behaviour. Consider import/export of tokens; avoid a second styling authority.
- [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs): constrained generation can guarantee schema conformance under specified conditions, not true values, valid domain semantics or aesthetics. Always validate at host boundary; model-neutral schema and structured errors.
- [Taffy](https://docs.rs/taffy/latest/taffy/), [Parley](https://docs.rs/parley/latest/parley/): retain proven layout and shaping unless measured evidence disproves suitability; use intrinsic sizing, baselines, grid/flex and accurate shaping rather than homegrown text/layout maths.
- [AccessKit](https://github.com/AccessKit/accesskit), [architecture](https://github.com/AccessKit/accesskit/blob/main/ARCHITECTURE.md), [WCAG 2.2](https://www.w3.org/TR/WCAG22/): accessibility tree, incremental updates and action requests. Generate native accessibility projection from same authoritative semantic tree; accessibility is not an optional AI substitute. Use relevant WCAG criteria as design/test guidance, not unsupported native compliance claims.
Check source licenses and attribution before code or asset reuse; prefer independently implementing ideas and importing compatible code selectively. Keep an ADR for each external dependency and version.

## 3. Current code inspection and diagnosis
Read directly at main: README, Cargo.toml, previous next-chapter doc, core, blocks catalogue and builder, theme, layout, inspector, shell, Workbench opening. Not a full code audit or native run. Prior Basic Memory status records 042–044 merged; historic CI/pipeline measurements do not prove physical responsiveness today.
- Core Component has stable ID, role, parent/children, visible/enabled, string-to-string props; App contains revision, commands and string state. Its public add panics on duplicate and can accept a nonexistent parent. Treat incoming authored plans as untrusted; validate before touching core. No uncontrolled direct state mutation.
- Blocks already implements reusable composite builders on the canonical tree; catalogue names layout, typography, card, indicator, metric and button primitives, with actions and defaults. This is the right starting seam, not a new independent UI tree. However arbitrary numeric padding/gaps/sizes and mostly prose/string property definitions expose too much presentation machinery at normal authoring level. Catalogue, typed structs, validators, docs and runtime must not drift.
- Theme already has five VisualWorlds and visual tokens; reuse; evaluate whether semantic type roles and responsive component recipes actually survive every profile. Font names alone don't ensure installed fallback or good shaping.
- Layout uses Taffy and Parley measurement; Eye compact_map already provides app and scene revisions, bounding rect, parent, visibility/clipping/overflow/enabled/z; detail includes props, text geometry with ink, trim, metrics, baseline, origin, line count, advance and clip. This is unusually useful. Extend, do not recreate it.
- Shell exposes HameshApp, event hooks, scene/layout caches and separate presented revision. Preserve reusable lifecycle, CPU/GPU measurement and inspection security; distinguish committed, laid-out and presented truth. Actual physical presentation remains a separate test.
- Workbench demonstrates command registry, menus and controls; Specimen is actual downstream client and acceptance harness. Neither a gallery nor headless tests alone demonstrate a pleasant app.
Hypothesis: the historical stagnation stems partly from solving layout at the primitive level without enough semantic, composition-level policy. This is not a proven explanation for every defect. The new prototype must outperform the old on evidence, not more abstraction.

## 4. Proposed architecture
One canonical domain state; one canonical retained UI representation; one coherent versioned resolved snapshot. No extra model is required at runtime.
A. Intent/authoring surface: versioned language-neutral ViewSpec, containing stable logical component identity, data bindings, declared importance, group and composition purpose, optional variant and capability references. Rust builder and JSON wire encode the same semantics. Schema-first machine catalogue generated from canonical types (or code generated from schema); no separate hand-maintained list. Expose compact discover -> detail/examples -> validate -> preview -> apply. Use schema-constrained generation where supported, but accept validated proposals from any model or human.
B. Presentation compiler: resolve trusted catalog, validate kinds/props/allowed parent/child/bindings/capability refs, type-check numeric units, detect cycles/duplicates/missing parents and budget violations. Expand recipes into existing core. Use typed resolved styles at compile/layout boundary; string props may remain as compatibility adapter until evidence supports removal. Stable logical IDs and derived subpart IDs survive reflow/theme. Reuse existing mechanisms rather than duplicate. Atomic candidate validation, then publish or retain last known good. Structured errors include path, rule, expected, actual, repair hint. Bounded deterministic repairs only (wrap/stack/density/overflow into approved alternatives), report choices; never silently discard controls or alter meaning.
C. Design grammar: semantic tokens -> component recipes -> composition recipes. Normal authors cannot arbitrarily set font/margin/absolute coordinates/colour. Semantic roles: page title, section, body, label, annotation, numeric display, unit, tick, monospace data, warning. Resolve font family/fallback/size/weight/line-height/spacing, baseline and tabular figures, locale, text scale and contrast centrally. Distinguish optical ink/trim and line box; correct typography shared by render and measurement. Components declare slots, grouping, intrinsic min/preferred/max, grow/shrink, aspect, content priority, fallback variants, allowed placements, overflow policy, keyboard/accessibility. Page compositions: instrument+related controls, inspector, document+sidebar, dashboard summary/details, toolstrip, list/detail. Add small curated examples and anti-examples. Layout engine chooses recipe and breakpoint by actual measured available space, not screen class alone; maintain semantic adjacency, reading order, focus, stable IDs; avoid arbitrary shrink-to-fit. Intentional scroll, truncation with reachable full content, overlays or canvas overlap are legal when explicit. Lint unintended overlap/clipping, invalid hierarchy, poor contrast, out-of-scale fonts, oversized empty space (heuristic only), misaligned baselines and excessively crowded groups. Error vs warning vs subjective review; never claim a universal beauty score.
D. Resolved projection (Eye): preserve map/detail, add component kind/version, domain object reference, purpose, stable relations (controls, labels, belongs_to, aligned_with, grouped_with), binding provenance, actual bounds/clip/visibility/occlusion, resolved theme/type roles/metrics, layout variant, diagnostics, current state and capability refs. Query viewport/units/DPI, app/scene/presented revision and snapshot freshness; never combine mismatched revision data or assert unseen pixels. Map summarized per group, on-demand details; bounded revision diffs/subscriptions, resync on gap. Compute geometry from actual resolved layout/scene, not authoring spec or AI narration. Layout and semantic event revisions may differ from high-frequency telemetry sequence; link accurately.
E. Hand: discover typed domain actions, argument schema, preconditions, authority, effect, reversibility; invoke against expected app/domain revision with idempotency key and explicit mechanism; return accepted/rejected/stale/denied, actual effect, revisions, evidence and undo when available. Human keyboard/pointer/accessibility and direct actions share application command/state path where appropriate; direct invocation does not prove human UI route. Never permit arbitrary generated code, filesystem paths, network access or hidden capabilities via ViewSpec. Data returned by apps is untrusted data, not agent instructions. Separate read/write/subscribe and sensitive sensory permissions, session/app scope, default deny. Use existing inspector CLI/MCP and revise schemas deliberately; no duplicate bridge.
F. Memory/Oracle: bounded structured traces for validation, layout, input, revisions, latency and failure evidence; retain existing Memory semantics. Oracle adapter receives sampled structured timings/events, never synchronous work in render/audio loop; no prompts, document text or audio in telemetry by default. Keep offline/no-model operation, lightweight local execution, redaction, quotas. Terror Bats attacks failure modes; Oracle measures ongoing reality.
G. OS boundary (deferred): apps expose namespaced object descriptors, meaningful events and capabilities through Hamesh. Omen discovers authorised commands, window manager reads spatial hints and controls tiling/floating/attached/pinned objects; external intelligence service owns relevance, persistent intents, attention, preferences and delegation. Switchboard/job infra supplies evidence; not dependencies of layout. Cross-app links use namespaced stable references and explicit capability grants; no global shared mutable GUI state. User correction inspectable/reversible; no focus theft; three modes no AI / AI assist / delegated task.
H. Portability: existing Rust core and shell, language-neutral schema/ABI/IPC boundary, Python proof before further bindings. Accessibility via AccessKit projection of same state, not fabricated names or extra tree truth. Do not claim Mac/Linux compatibility without actual platform runs.

## 5. First proof: audio instrument (not a DAW)
Reference: user's screenshot of the generated Input signal card on 2026-11-24. Strong hierarchy, compact label, large number, subordinate units, restrained surface, segmented meter. Preserve aesthetic character, but correct numerical fidelity: the example uses evenly spaced tick labels with unequal dB intervals and independently chosen lit segments; require the meter, tick positions, text and clipping state to derive from a single scale definition. For a linear -60..0 dBFS scale, -36 sits at 40%, -24 at 60%, -12 at 80%, -12.4 at ~79.3%; intentional nonlinear mapping must be declared and applied consistently. Choose linear-in-dB mapping initially. Define peak vs RMS; silence, overrange, stale/unavailable, clip latch/reset, tick collision, long labels, value sign/decimal and unit wrap must all be explicit. Never imply live input if using generated fixture.
Example conceptual proposal, not final protocol:
```json
{"kind":"InstrumentGroup","id":"input","primary":{"kind":"AudioLevel","id":"input.level","label":"Input signal","bind":"track.1.peak_dbfs","unit":"dBFS","scale":{"min":-60,"max":0,"mapping":"linear_db"},"prominence":"primary"},"controls":[{"kind":"Gain","bind":"track.1.gain_db","action":"track.1.set_gain"},{"kind":"Mute","bind":"track.1.muted","action":"track.1.set_mute"}]}
```
Runtime binds sample from fixture or application; recipe resolves visual sizes, orientation, palette, meter segments, ticks, focus. Add small waveform view from deterministic fixture with time domain, peak envelope, selected interval and zoom/seek capability. No actual audio engine, plugin hosting or DSP in this slice. Audio real-time thread never calls UI or AI; when live source added, coalesced bounded samples on UI thread and optional separately authorised excerpt for timbre. No per-frame agent prompts. Use same underlying value and mapping for human and Eye. Include related gain/mute controls so composition, not single card, is tested.
Eye can return exact group/layout role, actual positions and text geometry, data state/timestamp, scale definition and related actions. Hand adjusts gain/mute or selection, checks receipts and resulting Eye state without image access. Distinguish input level vs gain and sample peak from clip latch. Build second distinct surface (job/attention) only after the instrument group passes.

## 7. Verification contract
Hard gates: zero crashes, unintended overlap/clip or lost required content in agreed fixture matrix; correct numeric scale at endpoints/midpoint/thresholds, no fabricated telemetry; correct keyboard focus and available accessible names/actions; state/visual revision consistency; zero screenshot calls in defined routine agent task; stale/unauthorised/replayed actions cannot mutate state; no hidden code execution; successful native interaction and independent receipts. Intentional overflow documented and full content reachable. Run fmt/clippy/workspace tests, targeted CLI/MCP drills and native desktop checks; preserve existing tests or explicitly replace with stronger tests, never weaken to get green.
Proposed measurement budgets, finalise after baseline: frame pipeline p95 <=16.7ms for agreed 60Hz workload on reference hardware, input-to-present p95 <=50ms (measure method explicitly; software present not physical photon), idle no self-triggered redraw, no >10% regression in comparable memory/p95 vs accepted baseline without documented reason. Eye compact summary target <=2KB for small fixture, detail <=4KB, diff bounded with resync; measure actual tokenisation and response latency, do not impose these sizes on arbitrary large pages. A/B same hardware, build flags, data, DPI, sequence; report p50/p95/p99, max and misses, allocations, RSS, CPU vs GPU, layout/shape/scene/paint/present breakdown. Warmup and repeated trials. Test 1,000 updates, rapid resize, DPI and fonts, repeated theme switching, hidden/overlaid components, cross-app cache isolation, invalid schema and malicious strings, revision races, duplicate ID/missing parent, callback lifetime, disconnect/reconnect and resource exhaustion; cap payload sizes/depth/actions and compilation time. A11y contrast targets 4.5:1 normal, 3:1 large text/nontext where applicable; verify keyboard and native assistive technology, not numerical contrast alone.
Aesthetic gate: user plus independent reviewer compare rendered reference, old candidate and new variants at actual sizes. Judge hierarchy, rhythm, legibility, grouping, consistent numbers, purposeful spacing, appropriate density, genuine profile distinction. No averaging away critical defects. Do not use an AI screenshot score as sole approval. Track repair rounds, tokens, number of manual style overrides and unresolved diagnostics. If new grammar fails to beat old, stop and revise; don't add twenty widgets to camouflage failure.

## Summary
Beautiful by construction, understandable by construction, operable by contract, verifiable by evidence.
